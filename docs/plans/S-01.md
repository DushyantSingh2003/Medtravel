# S-01 — Monorepo scaffold

## Goal

Create the `medtravel` pnpm + Turborepo monorepo described in `docs/BUILD_PLAN.md` section 3:
four apps (`api`, `worker`, `web`, `portal`) and eight packages (`db`, `contracts`,
`api-client`, `ui`, `i18n`, `emails`, `pdf`, `config`), TypeScript strict throughout, Node 22,
with `pnpm install && pnpm check` green and `pnpm build` building every app.

## Stack versions actually used

`docs/BUILD_PLAN.md` was written against an older generation of these tools. The registry now
serves substantially newer majors, and the official generators (`create-next-app`,
`@nestjs/cli new`) produce a different shape than the plan assumes. This task follows the
generators rather than the plan's prose wherever the two disagree, because the generated
output is what the toolchain actually supports.

## Layout

```
medtravel/
├─ apps/      api (NestJS+Fastify) · worker (NestJS standalone+BullMQ) · web (Next) · portal (Next)
├─ packages/  db contracts api-client ui i18n emails pdf config
├─ e2e/       Playwright workspace (placeholder spec until there are flows to test)
└─ docs/      plans/ progress.md questions.md
```

## What each workspace contains at the end of S-01

- **apps/api** — NestJS on the Fastify adapter; `nestjs-zod` for validation; Swagger at `/docs`;
  pino logging through `nestjs-pino` with PII redaction (`authorization`, `cookie`, `password`,
  `otp`, `token`, `*.passport`, `*.email`, `*.phone`); `@fastify/helmet`; CORS from config;
  a `ConfigModule` validating `process.env` against a Zod schema at boot; `GET /health`.
  No business modules — those are F-01 onward.
- **apps/worker** — NestJS standalone application, BullMQ connected to Redis, one example queue
  (`notifications`) with a processor that logs, to prove the wiring.
- **apps/web** / **apps/portal** — Next.js App Router, Tailwind 4, `next-intl` with `en` and `ar`,
  `[locale]` segment, `dir="rtl"` on the html element for `ar`.
- **packages/config** — the shared presets: `eslint`, `prettier`, `tsconfig` bases
  (`base`, `nest`, `next`, `react-lib`) and a `vitest` preset.
- **packages/db** — Prisma, PostgreSQL datasource, schema with no models yet, scripts
  `db:migrate`, `db:seed`, `db:studio`, and a `PrismaClient` singleton export.
- **packages/contracts** — Zod schemas shared by API and UI; at this stage only the shared
  primitives (pagination, id, locale) so the dependency edge exists and is type-checked.
- **packages/api-client** — orval configuration pointed at the API's OpenAPI document, plus the
  TanStack Query provider. Generation runs via `pnpm api:generate`; the generated output is
  gitignored and regenerated, so this package ships only config + provider until the API has
  endpoints.
- **packages/ui** — Tailwind 4 theme CSS shared by both Next apps, plus a first component
  (`Button`) to establish the pattern and prove the build.
- **packages/i18n** — `en` and `ar` message catalogues and the locale list.
- **packages/emails** — React Email, one `WelcomeEmail` template.
- **packages/pdf** — `@react-pdf/renderer`, one minimal document template.

## Root scripts

`dev`, `build`, `check` (lint + typecheck + test), `e2e`, `api:generate` — all Turborepo tasks
except `api:generate`, which runs orval against the API.

## Environment files

`.env.example` for `api`, `worker`, `web`, `portal` and `packages/db`. No real `.env` is created
or committed, per the autonomous rules.

## Tests

S-01 adds no features, so tests are the ones that prove the scaffold works: the API's
`/health` e2e test, the worker's queue-wiring unit test, a `packages/contracts` schema test and a
`packages/ui` render test. The acceptance check for this task is `pnpm check` green and
`pnpm build` building all four apps.

## Assumptions

- **Linting.** The plan calls for a shared ESLint preset in `packages/config`, but NestJS 12's
  generator now emits `oxlint` while Next's emits ESLint 9. Chose one shared ESLint 9 flat config
  for the whole repo (Next apps additionally spread `eslint-config-next`), because the plan asks
  for a single shared preset and `eslint-config-next` cannot be replaced without losing the Next
  lint rules. Recorded in `docs/questions.md`.
- **TypeScript version.** NestJS 12's generator picks TS 6 and Next 16's picks TS 5. Verified
  that Next 16 builds and lints on TS 6, then used `^6.0.2` in every workspace.
- **Prisma.** The `latest` dist-tag is a release candidate (`8.0.0-rc.22`); pinned the stable
  `7.10.0` instead. Worth revisiting when 8 is released.
- **Tailwind preset.** Tailwind 4 has no JS config file, so the plan's "Tailwind preset" in
  `packages/ui` is a shared CSS file with an `@theme` block that each app imports.
- **api-client.** `pnpm api:generate` exports `apps/api/openapi.json` by booting the Nest app
  without listening, then runs orval. Both the document and the generated output are gitignored.
- **Local services.** `infra/docker-compose.yml` belongs to S-02, so S-01 does not create it.
  Tests that need Postgres or Redis arrive with the tasks that need them.
- **mobile/** — Phase 2 in the plan, not created.

## Defects found by running the apps (not by `pnpm check`)

Unit tests and `pnpm check` were green while four real problems remained. Booting the built
apps found them:

1. Swagger on Fastify needs `@fastify/static`; without it the API process exited at startup.
2. BullMQ on native ESM cannot lazy-load ioredis; the worker looped on errors until given a
   constructed client.
3. `api:generate` failed because nothing exported the OpenAPI document first.
4. Reading `NEXT_PUBLIC_API_URL` with bracket notation would not have been inlined by Next, so
   the browser client would have ignored its configured base URL.
