# AD-01 — Users and roles

## Goal

The super admin manages staff: invite, change role, team, city, languages, working hours and leave; deactivate (signs the person out
everywhere within seconds), reset their two-factor, read their login history; group people into teams with managers; look at the
product as another user, read-only and fully audited, with a banner. Acceptance: deactivating a user logs them out everywhere
within seconds.

## Design

- **Data** (migration `ad_01_users`): `Team` (name, manager); `StaffProfile.teamId` and `workingHours` (JSON: time zone and per-weekday
  intervals); `StaffLeave` (user, first and last day, note); `AuditEvent.onBehalfOfId` (who was being looked at when an admin
  impersonated). Assigning a team sets the profile's `managerId` to the team's manager, so the existing case scoping (a manager sees
  the team's cases) keeps working. A person has one role (the schema's `User.role`); one city.
- **API** (`/admin/users`, `/admin/teams`; subject `User`, super admin only): list (cursor, search, role/status/team/city), get,
  update (name, role among the staff roles, title, languages, city, team, assignable, open-case cap, working hours, timezone), add
  and remove leave, deactivate and reactivate, reset two-factor, login history (the `auth.*` audit rows of that user), teams CRUD.
  Staff are invited with the existing `POST /auth/invitations`.
- **Deactivate**: in one transaction set the status, revoke every session, delete one-time challenges, audit and queue an event;
  after the commit disconnect the person's sockets through Redis and push `session.revoked` to their room. The HTTP guard already
  checks the user's status on every request, so the next call fails with 401 at once. You cannot deactivate yourself or the last
  active super admin.
- **Force 2FA reset**: clears the second factor and backup codes, revokes sessions (the person signs in again and, as staff, is sent to
  set it up), audits, and queues a notification to the person.
- **Impersonation**: `POST /admin/users/:id/impersonate` sets a signed, httpOnly `mt_imp` cookie (30 minutes, tied to the admin's
  session). While it is present the guard makes the target the acting user, read-only: every unsafe method is refused (403) except
  `POST /auth/impersonation/stop`. Only super admins, only active non-admin users, not yourself. Every request made while impersonating
  writes an audit row (`impersonation.request`: method and route pattern) and every audit row of that request names the admin as the
  actor and the viewed user in `onBehalfOfId`. `/auth/me` returns `impersonating` so the portal shows a banner with a stop button.
- **Portal**: `/admin/users` (list with filters), a detail page with tabs (profile, working hours and leave, login history), an invite
  dialog, deactivate and reset dialogs, teams, an impersonation banner in the shell, and a realtime `session.revoked` handler that
  signs the browser out immediately.

## Assumptions

One role per person; one city per person; teams are flat. Impersonation does not cover the realtime channel (sockets use the admin's own
cookies) and refuses to start for another super admin.
