# F-03 — Authentication

## Goal

Real sign-in for every role (PRD 5.2, 12): email + password, or a one-time code by email or phone for patients, attendants and
agents; TOTP two-factor with backup codes (mandatory for staff, hospital and admin users); rotating refresh tokens,
a device list and "log out other sessions"; password reset, email verification, lockout, rate limits and CSRF
protection; invitations and a 72-hour magic link for doctors; the portal pages for all of it. The stub sign-in of S-06
and F-02 goes away.

Acceptance: each seed role can log in and lands on its own portal; staff cannot skip 2FA.

## Design

- **Sessions.** A sign-in creates a `Session` row. Two cookies, both `httpOnly`, `SameSite=Lax`, `Secure` in production:
  `mt_at` (access token, 15 minutes, an HMAC-signed `{sid, uid, exp}`) and `mt_rt` (refresh token, `<sessionId>.<secret>`,
  30 days, path `/auth`). Only `sha256(secret)` is stored. A refresh rotates the secret and keeps the previous hash; a
  replayed old token revokes the session (stolen-token detection). Every request checks the session row, so logout and
  "log out other sessions" take effect at once. API clients may send `Authorization: Bearer <access token>`.
- **CSRF.** For an unsafe request authenticated by cookie the `x-csrf-token` header must equal the readable `mt_csrf`
  cookie (double submit). Any unsafe request with an `Origin` header must come from `CORS_ORIGINS`.
- **Second factor.** `User.twoFactorSecret` holds the TOTP secret encrypted with AES-256-GCM (`AUTH_ENCRYPTION_KEY`).
  Login with 2FA enabled returns a 5-minute signed challenge token; the code (or a backup code) turns it into a
  session. A user whose role requires 2FA but has none enrolled gets a **limited** session (`access: two_factor_setup`):
  the guard refuses everything except the 2FA setup endpoints and `me`/`logout` until they enrol. Wrong codes count
  towards the lockout. `AUTH_DEV_SKIP_2FA=true` skips the requirement for users without 2FA, only when `NODE_ENV=development`.
- **Lockout and rate limits.** Five wrong passwords or codes lock the account for 15 minutes. An in-memory limiter
  (per IP and per email/identifier) guards login, OTP, forgot-password, register and invitation endpoints; a shared
  store (Redis) replaces it when the API runs on more than one instance.
- **One-time secrets** (`AuthChallenge`): email verification, password reset, sign-in codes, invitations, magic links.
  Only hashes are stored; sign-in codes are 6 digits, 10 minutes, 5 attempts. Requests that would reveal whether an
  address has an account (register, forgot password, code request) answer the same way for known and unknown addresses.
- **Mail.** `Mailer` is a port: `capture` (default in development and test; keeps messages in memory and logs only that one
  was sent) or `smtp` (nodemailer, Mailpit locally). Real templates and channels arrive with F-07.
- **Invitations.** The admin invites staff and hospital users, a hospital desk its own hospital's doctors and desk users,
  a patient their attendants. Accepting sets the password and creates the user (and the hospital or attendant link).
- **Magic link.** A hospital desk sends a doctor a link for one case the hospital has received (an `OpinionRequest`);
  redeeming it opens a session of kind `magic_link` limited to that case (`scopeCaseId`), no password, 8 hours at most.
  Such a session cannot touch account, 2FA or invitation endpoints.
- **Guard.** `AuthGuard` replaces `StubAuthGuard`; `Actor` carries `userId`, `role`, `sessionId`, `scopeCaseId`. Routes
  declare `@Public()`, `@Authenticated()` (any signed-in user) or `@Can(...)`. Audit rows now carry a real actor.

## API (all under `/auth`)

| Endpoint                                                                                                  | Access                                                          |
| --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `POST register`, `POST email/verify`, `POST password/forgot`, `POST password/reset`                       | public, rate limited                                            |
| `POST login`, `POST login/otp/request`, `POST login/otp/verify`, `POST 2fa/challenge`, `POST refresh`     | public, rate limited                                            |
| `GET invitations/:token`, `POST invitations/accept`, `POST magic-links/redeem`                            | public                                                          |
| `GET me`, `POST logout`, `POST logout-others`, `GET sessions`, `DELETE sessions/:id`, `POST email/resend` | signed in                                                       |
| `POST 2fa/setup`, `POST 2fa/enable`                                                                       | signed in, also with a limited session                          |
| `POST 2fa/disable`, `POST 2fa/backup-codes`, `POST password/change`                                       | signed in, full session, not magic link                         |
| `POST invitations`, `POST magic-links`                                                                    | signed in, by role (`canInvite`; hospital desk for magic links) |

## Portal

`/login` (password and code tabs), `/login/code`, `/two-factor`, `/two-factor/setup`, `/forgot-password`, `/reset-password`,
`/accept-invitation`, `/verify-email`, `/magic`, `/account/security` (devices, log out others, 2FA, password). The portal
reads the session from the API (`GET /auth/me` with the browser's cookies) instead of the stub cookie.

## Data model

Migration `f_03_auth`: `Session` gains `kind`, `previousTokenHash`, `deviceLabel`, `twoFactorVerifiedAt`, `scopeCaseId`;
`User` gains `emailVerifiedAt`, `phoneVerifiedAt`, `passwordChangedAt`, `failedLoginCount`, `lockedUntil`; new tables
`AuthChallenge` and `BackupCode`; checks for the counters, challenge secrets and magic-link scope.

## Dependencies

`@node-rs/argon2` (argon2id with prebuilt binaries, no compiler needed in the image), `otplib` (TOTP), `qrcode` (enrolment QR),
`nodemailer` (SMTP). Cookies, CSRF, throttling and tokens are written directly (a few dozen lines each) rather than
pulling plugins.

## Seed

`pnpm db:seed` creates one development user per role (see `docs/dev-users.md`, password `Dev@12345`), only when
`SEED_DEV_USERS=true` and never when `NODE_ENV=production`; plus one user with 2FA enabled and a fixed secret for tests.

## Tests

Unit: tokens, access token signing, secret box, password policy, TOTP, lockout arithmetic, throttle, cookie
building. API e2e (real PostgreSQL): every endpoint, forbidden roles, lockout, rotation and replay, CSRF, 2FA enforcement,
OTP, reset, invitations, magic link scope, enumeration-safe answers. Playwright: every seed role signs in and lands in
its portal; staff are forced into 2FA setup and cannot skip it; forgot/reset, device list.
