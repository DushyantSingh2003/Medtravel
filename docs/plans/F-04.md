# F-04 — Roles, permissions and data scoping

## Goal

One permission matrix (role × subject × action, with a data scope and field-level rules) for the 11 roles of PRD section 2,
used by the API guard (`@Can`) and the portal (`useCan`); one place that turns a role's scope into a database filter;
a table-driven test suite over every role and subject; `docs/permissions.md` generated from the matrix.

Acceptance: the permission test suite passes and an agent account gets 403 on any document endpoint.

## Design

- **Matrix** (`packages/contracts/src/permissions.ts`, `permission-matrix.ts`): for each role, for each subject it can touch:
  the actions (`read create update delete export`), the **scope** (who's data: `all`, `own`, `team`, `city_window`,
  `hospital`, `assigned`, `referrals`, `attached`) and, for `Case` and `Patient`, the **field groups** it may read.
  Anything not listed is denied. `can(role, action, subject, field?)` is built on CASL (`@casl/ability`, new dependency:
  small, no runtime dependencies, the library the task names) so field checks and `subject` checks use one engine in the API
  and the browser.
- **Scoping in one place** (`apps/api/src/rbac`): `ScopeService` turns the actor's role and links (staff profile, hospital
  staff, doctor, agent user, patient, attendant) into Prisma `where` filters: `caseWhere(actor)`, `documentWhere(actor)`,
  `patientWhere(actor)`, and `assertCaseAccess(actor, caseId)` (404 for a case outside the scope, so existence is not
  revealed). Modules never write their own role checks. A magic-link session (`scopeCaseId`) is narrowed to that one case
  here, which closes the F-03 deferral.
- **Scope rules** (assumptions in `docs/questions.md`):
  - patient: cases of their own patient record; attendant: cases they are attached to (`CaseAttendant`).
  - agent: cases with their agency's `agentId` (every agent user of the agency), never documents; fields limited to case
    number, name, stage and status; never medical data or money.
  - case manager: own cases and the cases of their team (same manager); a manager (`StaffProfile.isManager`) sees all.
  - ground coordinator: cases in their city with a planned arrival within ±30 days (city of the hospital, else the
    preferred city).
  - interpreter: cases with a booking assigned to them; medical reviewer: cases they review, plus unassigned cases in
    medical review.
  - hospital desk: cases sent to their hospital (an `OpinionRequest` that left draft); doctor: only cases assigned to them
    (an opinion request with their doctor id).
  - finance and super admin: all cases (finance sees money fields, never medical ones).
  - Documents: patient/attendant their own; staff roles with the matrix permission; hospital users only documents shared with
    their hospital by a live consent (`DocumentShare`, consent not withdrawn); agents none.
- **Portal**: `PermissionsProvider` (role from the session) and `useCan(action, subject, field?)`.
- **Docs**: `pnpm --filter @medtravel/contracts docs:permissions` writes `docs/permissions.md`; a test fails if it is stale.

## API

No new endpoints. `PermissionsGuard` keeps its contract; every route's `@Can` must be satisfiable by at least one role
(inventory test). The acceptance check uses a test-only controller with `@Can('read', 'Document')` because the real document
endpoints arrive in F-06.

## Tests

- contracts: table over every role × subject × action against the matrix, explicit invariants (agent never reads Document,
  MedicalSummary, Opinion, Quote, Invoice or Payment; only super admin changes users; patients cannot touch staff subjects;
  hospital roles cannot read money), field rules, generated doc is current.
- API e2e (real PostgreSQL): `ScopeService` against fixtures for all 11 roles (which cases each sees), documents consent
  rule, magic-link narrowing, and a 403 for an agent (and a patient) on a document route; 200 for a permitted role.
- Portal: `useCan` unit test.
