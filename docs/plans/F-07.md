# F-07 — Notification engine

## Goal

One way to tell a person something: `NotificationService.send(eventKey, recipients, data)` looks the event up in a registry,
picks the channels the person wants and may receive, renders the message in their language, queues one delivery per channel,
retries with backoff, and keeps a log of what happened to each message (queued, sent, delivered, read, failed).

Acceptance: firing a test event sends email + in-app (+ WhatsApp in the sandbox) in the recipient's language and shows in the log.

## Design

- **Registry** (`packages/contracts/src/notification-events.ts`): every event of PRD section 10 (19 patient, 7 internal, 3 agent)
  plus `document_quarantined`, `incident_created` and `test_event`. Each has an audience, a category (`security` cannot be
  switched off), its default channels and the names of its variables. The text of each event in English and Arabic lives
  in `packages/notifications/src/templates` (code, reviewed like any other change; Arabic is machine-drafted and listed in
  `packages/i18n/REVIEW.md`). Template text uses `{name}` placeholders; a missing variable is an error in tests, an empty
  string in production.
- **Package `@medtravel/notifications`** (used by both API and worker so there is one implementation):
  `render` (text, email HTML through React Email in `packages/emails`, WhatsApp template parameters), provider interfaces
  `EmailProvider`, `SmsProvider`, `WhatsAppProvider` and their adapters (SMTP for SES and Mailpit; SMS: MSG91, Twilio; WhatsApp: Meta Cloud API, which
  every BSP exposes; and `dev` adapters that deliver SMS and WhatsApp text to Mailpit as email so one inbox shows
  everything), `enqueueNotification(tx, …)` (writes rows and outbox events inside the caller's transaction) and
  `deliverNotification(prisma, id, providers)` (called by the worker).
- **Flow**: a service calls `send(tx, …)` in the transaction of the change. For every recipient and channel allowed by the
  user's preferences and available (an email address, a verified phone) it inserts a `Notification` row (`queued`, key
  `<eventKey>:<dedupe>:<user>:<channel>`) and an outbox event `notification.deliver`. The in-app row is `sent` at once. The worker
  claims the event, renders and calls the provider, then sets `sent` and the provider's message id. A provider failure throws, so
  the outbox retries with its exponential backoff and the row records the attempt count and last error; after the last attempt
  the row is `failed`. Redelivery of an event never sends twice (a row already `sent` is skipped).
- **WhatsApp**: a template message (approved name + ordered variables) is always allowed; free text only if the person wrote to us in the
  last 24 hours (`Message` inbound on a WhatsApp conversation), otherwise the template is used.
- **Delivery status**: `POST /webhooks/notifications/:provider` (public, rate limited, HMAC-signed with
  `NOTIFICATION_WEBHOOK_SECRET`; provider payloads parsed by the adapter) moves a row `sent → delivered → read` or to `failed`,
  never backwards, once per provider event (`ProcessedWebhook`).
- **Preferences**: `NotificationPreference(userId, channel, enabled)`; `GET/PUT /notifications/preferences`. In-app and
  `security` events cannot be switched off. Default is on.
- **API**: `GET /notifications` (own, cursor), `GET /notifications/unread-count`, `POST /notifications/read`, preferences,
  `GET /notifications/log` (super admin; filters channel, status, event, user, date) and `POST /notifications/test`
  (super admin; sends `test_event` to a chosen user or oneself). Subject `NotificationLog` (new) guards the last two.
- **Existing code moved onto the engine**: the document quarantine and incident notices (were hand-made rows); the
  auth mailer's SMS branch now calls the SMS provider (still never logged: codes are secrets).
- **Portal**: bell dropdown in the shell header (polls every 30 s; push arrives with F-08), a preferences page
  (`/account/notifications` under every portal's account menu is out of scope: the patient and the admin portals get it at
  `…/settings/notifications`), and `/admin/notifications` (the log with filters, detail and a "send a test" dialog).
  Components `NotificationList`, `NotificationBell` in `packages/ui`, with gallery entries in en and ar.

## Tests

Registry spec (every event has en + ar text for each channel it uses, every placeholder is a declared variable, ar has
no Latin-only text), render spec, adapter specs against a local HTTP server, API e2e (send, preferences, dedupe, read, log,
test event, forbidden roles, webhook signature and ordering), worker e2e (deliver, retry, fail, WhatsApp window, language),
Playwright (bell, preferences, admin log + test event, Arabic).

## Assumptions

Templates are code, not database rows editable in the admin (the plan says "seeded"; a table can follow when a screen is asked
for). Recipients must be users (a lead without an account is notified when C-01 creates one). No quiet hours. Real SES, MSG91,
Twilio and Meta endpoints are never called in tests; their adapters are exercised against a local HTTP double.
