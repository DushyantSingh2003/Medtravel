# F-10 — Case core and stage machine

## Goal

One place that decides how a case moves: the twelve stages, the exit stages, what each move needs, who may make it, how long
each stage should take, and what follows automatically. Acceptance: the full transition test matrix passes.

## Design

- **State machine** (`packages/contracts/src/case-machine.ts`, pure functions, no database): `describeTransition(from, target)`
  answers allowed or not (with a reason) and, if allowed, the resulting `{ stage, status }` and the data it needs
  (`owner_assigned`, `medical_summary`, `sent_quote`, `accepted_quote`, `deposit_paid`, `lost_reason`, `note`).
  `missingRequirements(requires, facts, input)` lists what is lacking. Targets are the twelve stages, `lost`, `on_hold`,
  `cancelled` and `closed` (a follow-up case that is finished: the stage stays `follow_up`, the status becomes `closed`).
  - Forward one stage; back one stage (needs a note); any open stage to `lost` (reason), `on_hold` (note), `cancelled` (note).
  - `on_hold` and `lost` go back only to the stage the case left (`resumeStage`, found in the stage history); `lost` needs a note
    to reopen. `cancelled` and `closed` are final. `on_hold` may still become `lost` or `cancelled`.
  - Status per stage: new, qualifying, in_medical_review, awaiting_opinions, quote_sent, won (booking_deposit), visa_in_process,
    travel_booked, arrived, in_treatment, discharged, returned_home, follow_up.
  - **Won needs a deposit**: leaving `booking_deposit` for `visa` needs a succeeded deposit payment, or `override: true` with a
    note (finance, case manager, super admin).
  - Who may move a case: super admin and case manager always; any other role only while it is the owner role of the stage the case
    is leaving. Patients, attendants and agents never.
  - Owner role and default target minutes per stage, and the automatic tasks created on entering a stage (code defaults, e.g.
    entering `travel_planning` creates "Book airport pickup" for the ground coordinator).
- **Database** (migration `f_10_cases`): `StageConfig` (one row per stage: target minutes, owner role, auto-task list) overrides the
  code defaults and is edited by the super admin (API now, screen later); `Case.slaBreachedAt`; `Task.assigneeRole` plus a unique
  `(caseId, autoKey)` so re-entering a stage does not create the task twice.
- **CaseStageService.transition()** is the only code that changes `Case.stage`. One transaction: lock the case row, load the
  facts, check the machine and the actor's role and scope, update stage/status/`stageEnteredAt`/`slaDueAt`/`closedAt`/lost
  fields, write the stage history, create the auto-tasks, audit and queue `case.stage_changed` (outbox).
- **Case numbers** `CASE-YYYY-NNNNNN` from `NumberSequence` inside the creating transaction.
- **API** (`/cases`): create, get, list (cursor, filters, sort), `POST /cases/:id/transitions`, `GET /cases/:id/history`,
  `GET/PUT /cases/stage-config`. Scope from `ScopeService.caseWhere`; a case outside scope is a 404.
- **Worker**: handler for `case.stage_changed` (realtime push to the case room, patient notification where one exists) and a
  per-minute SLA sweep that marks overdue cases (`slaBreachedAt`) and queues the `sla_breach` notification once.

## Assumptions

Recorded in `docs/questions.md`: Won is the status while the deposit is awaited and confirmed on leaving `booking_deposit`; only
data the schema can already check is required (quotes, deposit, summary, owner); visa, travel and admission checks come with
those tasks.
