# F-08 — Realtime gateway

## Goal

Screens update without a refresh: the API holds Socket.IO connections (cookie-authenticated, several API instances behind a
Redis adapter), each person joins rooms for themself, their cases and their hospital after a permission check, and the portal
turns the events it receives into TanStack Query invalidations. A browser that was offline catches up on what it missed.

Acceptance: two browsers on the same case see each other's changes live.

## Design

- **Events** (`packages/contracts/src/realtime.ts`): `notification.created`, `case.updated`, `message.created`,
  `task.assigned`, `typing`. A payload carries ids and the time, never the content (`{ caseId }`, `{ notificationId }`): the
  client refetches through the normal, permission-checked API. Rooms: `user:<id>`, `case:<id>`, `hospital:<id>`.
- **Connection** (`apps/api/src/realtime`): `GET /realtime` upgrade (Socket.IO path `/realtime`). The handshake must carry an
  allowed `Origin` (cross-site WebSocket hijacking) and the access cookie (or a bearer token); it is checked with the same
  `SessionService.authenticate` as every request. Limited sessions (no 2FA yet) are refused. Joining `user:<id>` is automatic.
  The session is re-checked every minute; a revoked or expired one is disconnected (`session_expired`), and the client
  refreshes its cookie through the REST API and reconnects.
- **Joining** (`join` message with an acknowledgement): `case:<id>` needs `ScopeService.assertCaseAccess` (so staff scoping,
  hospital consent, patient ownership and agent exclusion all apply; an agent never gets a case room); a magic-link session
  may join only its one case; `hospital:<id>` needs a `HospitalStaff` link. A refused join answers `{ ok: false }` and reveals
  nothing (same answer for a missing room and a forbidden one).
- **Typing** is the one client-to-server event: `typing { caseId, typing }` is relayed to the case room (not back to the sender)
  only if the sender has joined that room; rate limited per socket.
- **Publishing**: `@medtravel/realtime` (`publish(room, event, payload)`) sends through the Redis emitter (so the worker, which
  holds no sockets, can publish) and appends to a short log per room (last 200 events, one hour) used for catch-up. Business
  code writes an outbox event `realtime.publish` in its transaction, the worker publishes it after commit (never for a change
  that rolled back). `NotificationsService`/the engine write one for every in-app notification (`notification.created`).
- **Catch-up**: after a reconnect the client rejoins its rooms and sends `sync { since }` (the time of the last event it saw,
  server clock); the server replays the logged events newer than that for the rooms the socket is in. Events older than the log
  window cause a `resync` message, on which the client invalidates everything.
- **Redis adapter** (`@socket.io/redis-adapter`) with two ioredis connections; a Redis outage must not take the API down (the
  gateway starts without the adapter, logs once, and works for one instance).
- **Portal**: `useRealtime()` in the shell opens one socket (`socket.io-client`, `withCredentials`, reconnect with exponential
  backoff and jitter), maps events to query keys (`notification.created` → notification list; `case.updated`,
  `message.created`, `task.assigned` → registered keys of the case) and exposes `useCaseRoom(caseId)` (joins/leaves) and
  `useTyping(caseId)`. The bell now refreshes on the push and polls only as a 5-minute fallback.

## Tests

Contracts spec; gateway e2e against Redis with real `socket.io-client`s: unauthenticated, wrong Origin, limited session,
join allowed/forbidden per role (patient own case, other patient's case, agent, hospital without consent, magic link), typing
relayed only to the room and not to the sender, two instances through the Redis adapter, publish from outside (worker),
catch-up after disconnect, revoked session disconnects. Worker e2e for the `realtime.publish` handler and the in-app event.
Playwright with two browser contexts: a notification sent to one user appears in their open bell without a reload.

## Assumptions

Payloads carry ids only. The catch-up log lives in Redis and is best-effort (an hour, 200 events a room). Case rooms exist now
but no screen publishes `case.updated`/`message.created`/`task.assigned` yet: C-04, C-10 and C-09 call `publish` when they land.
