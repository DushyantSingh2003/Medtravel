# S-04 — CI pipeline and staging deploy

## Goal

GitHub Actions CI on every pull request (cached install, Turborepo cache, lint, typecheck, unit
tests, API e2e with a Postgres service container, build of every app, Playwright smoke test);
Dockerfiles for api, worker, web and portal (multi-stage, non-root, small); on merge to `main`,
push the images to Amazon ECR and roll the staging ECS services; a PR template; Dependabot for
npm and GitHub Actions; the required GitHub configuration documented in `docs/deploy.md`.

## What was added

- `.github/workflows/ci.yml` — four parallel jobs: *Lint, typecheck, unit tests*; *API e2e*
  (Postgres 16 and Redis 7 service containers); *Build all apps and smoke test* (builds
  everything, boots the API and website, runs Playwright); *Docker image* (matrix of the four
  images: build, then boot each one and check it responds).
- `.github/workflows/deploy-staging.yml` — on push to `main`: build the four images, boot-test each,
  push to ECR tagged with the commit and `staging`, then `update-service --force-new-deployment` and wait for
  stability. Authenticates with GitHub OIDC (no stored AWS keys). Does nothing until the
  `AWS_ROLE_ARN` variable is set.
- `infra/docker/node-service.Dockerfile` (api, worker) and `infra/docker/next-app.Dockerfile`
  (web, portal), parameterised by `APP`, plus a root `.dockerignore`.
- `scripts/smoke-image.sh` — boots a built image and checks it (non-root, endpoints answer, the
  worker stays up); used by CI and runnable locally.
- `.github/pull_request_template.md`, `.github/dependabot.yml`, `docs/deploy.md`.
- `.pnpmfile.cjs` — drops the Prisma CLI from `@prisma/client`'s optional peers so it does not
  ship in service images.

## Changes to earlier code

- **`packages/ui` now declares `tailwindcss`** (dev and peer dependency). `theme.css` does
  `@import 'tailwindcss'`, but the package never depended on it; the build only worked on this
  machine through an accident of module resolution and failed in a clean container (and would
  have failed in CI).
- **`apps/web` and `apps/portal` `next.config.ts`** emit a standalone server when
  `NEXT_OUTPUT=standalone` (set only inside the Docker build); `public/.gitkeep` added so the
  directory exists in a fresh clone.
- **`apps/api` and `apps/worker` `package.json`** gain `"files": ["dist"]` so `pnpm deploy`
  ships compiled output only.

No API endpoints, data model, permissions, UI or i18n keys change.

## Tests

CI itself is the deliverable. `scripts/smoke-image.sh` is the new test: it fails when an image
builds but cannot start. Existing unit, API e2e and Playwright tests are what the pipeline runs.

## Assumptions

- **CI also runs on pushes to `develop`**, not only pull requests, because the build loop merges
  task branches into `develop` without opening one.
- **Docker images are built (not pushed) on every pull request**, so a broken Dockerfile is caught
  before merge rather than on deploy. The task asked only for build-on-merge.
- **Mutable `:staging` tag.** ECS task definitions point at `:staging` and a forced deployment
  pulls the new image. This keeps task definitions static until Terraform (L-05); the commit-tagged
  image is pushed too, for rollbacks.
- **Deploy is dormant** until `AWS_ROLE_ARN` is set, and uses default names
  (`medtravel-staging` cluster, `medtravel-<app>` repositories) that can be overridden by variables.
- **Migrations are not run by the image** (it has no Prisma CLI); a one-off task or CI job is
  set up in L-05.
- **Alpine base.** Chosen for size. Re-check when a native module (`argon2`, F-03) is added.
- **Action versions** are major tags (`@v4` and so on) from memory; Dependabot keeps them current.

## Verification

Run in this environment:

- `actionlint` is clean on both workflows; `shellcheck` is clean on the smoke script.
- All four images were built from the real Dockerfiles and booted with `scripts/smoke-image.sh`
  (results in the final section below).
- A clean-container build found and fixed three defects that `pnpm check` and a local build had
  missed: the undeclared `tailwindcss` dependency, a worker that crashed in the image because
  `pino-http` (a required peer of `nestjs-pino`) was missing once peer installation was turned
  off, and the empty `public` directories.
- The CI steps themselves were dry-run locally in order (see below).

**Update after pushing:** `ci.yml` ran on GitHub for a push to `develop`. Run 1 failed only on the
worker image check (a bug in the smoke script, fixed); run 2 was fully green. The action versions
and `vars` usage in `ci.yml` are therefore confirmed. **Still not demonstrated:** CI on an actual
pull request (the same jobs, a different trigger), and the deploy workflow, which has never run
and needs AWS resources that do not exist yet.

## Review

An independent `code-reviewer` subagent reviewed the change (1 high, 4 medium, 6 low). All were
addressed except where noted:

- **High — Docker builds fail on any run that reuses the GitHub Actions layer cache.** The pnpm
  store lived in a BuildKit cache mount, whose contents layer caches do not export, so a cached
  `deps` layer plus an empty mount broke `pnpm install --offline`. Reproduced here by deleting
  only cache-mount data after a build (old pattern fails, store-in-layer passes). Fixed by
  removing the mounts from both Dockerfiles; all four images rebuilt and boot-tested again.
- **Medium — manual deploy from any branch.** The deploy job now requires
  `github.ref == 'refs/heads/main'`; docs say to restrict the `staging` environment's deployment
  branches to `main`.
- **Medium — wrong IAM trust guidance.** With an environment the OIDC subject is
  `repo:<org>/<repo>:environment:staging`; `docs/deploy.md` now states the exact condition.
- **Medium — empty `STAGING_API_URL`.** The deploy fails fast for web and portal when it is
  empty, and passes the build argument only to those two.
- **Medium — deploy not gated on CI.** Branch protection with the exact check names is now
  documented as required before enabling deploys, and the deploy boots each image
  (`scripts/smoke-image.sh`) before pushing it.
- **Low:** repository-versus-environment variables, mutable ECR tags and exact check names
  documented; CI no longer cancels in-progress runs on `develop`; Dependabot comment corrected
  and majors split out; `docs/progress.md` marks S-04 as pending its first GitHub run. Pinning
  third-party actions to SHAs is noted in the docs but not done.

## Results of the local runs

Images built from the real Dockerfiles (through the sandbox's proxy, with only the CA and proxy
injected into a scratch copy) and booted by `scripts/smoke-image.sh`: **api, worker, web and
portal all pass** and run as uid 1000. Sizes: api 469 MB, worker 470 MB, web 320 MB, portal 320 MB
(the `node:22-alpine` base is about 238 MB of each). The smoke script was also run against a
wrong image and against a root-user image and correctly failed both.

CI job steps run in order from a clean copy of the tree (frozen-lockfile install, lint,
typecheck, unit tests, API e2e against a real Postgres container, build, boot API and website,
Playwright): all green, Playwright 4/4.

## Other findings

- `dump.rdb`, a Redis snapshot, had been committed in S-01. It held only a test key. Removed and
  `*.rdb` ignored.
- **First real GitHub run (develop, run 1):** lint/typecheck/tests, API e2e, build + Playwright and
  the web image boot all passed. The worker image boot step failed even though the image was fine:
  `scripts/smoke-image.sh` piped `docker logs` into `grep -q` under `pipefail`, so a SIGPIPE
  whenever grep exited at the first match made a present log line look absent (it passed locally by
  timing). Its failure output was also empty because the log was only captured in the exit trap.
  Fixed by reading the logs into a variable first and printing them from `fail()`; passed five
  consecutive local runs.
